# Real-world guardrails for an LLM alert-triage assistant

Research note, 2026-11-23. Question: what do primary sources recommend for an LLM assistant that reads SIEM alerts, calls read-only lookup tools, outputs a disposition with cited evidence, and proposes actions a human must approve?

This note does not repeat `docs/related-work.md` (Greshake, InjecAgent, Tsegai, ExCyTIn, CyberSOCEval, ASB, ALCE, CaMeL's headline result, the abstention survey). It adds the guidance and defenses around them.

How to read the tags:
- **measured**: the source reports a number from an experiment.
- **claimed**: the source recommends or asserts it, with no number.
- *(unverified)*: I could not open or check the source in this session.

## 1. Summary

- Every source agrees on one thing: you cannot reliably *detect* prompt injection, so limit what a successful injection can do. Beurer-Kellner et al. say detectors and filters "remain fundamentally heuristic and cannot guarantee prevention of all attacks" ([arXiv 2506.08837](https://arxiv.org/html/2506.08837v3)). OpenAI says classifier "AI firewalling" often misses fully developed attacks ([OpenAI](https://openai.com/index/designing-agents-to-resist-prompt-injection/)).
- In this project, actions are already structurally safe: tools are read-only and the approval gate never executes. What is *not* protected is the **disposition**. A planted "this is benign" can change it. That gap is where C failed (27% injection success, `docs/report.md`).
- Spotlighting (marking or encoding untrusted text) is the one cheap prompt-level defense with a strong measured result: attack success from above 50% to below 2% on GPT-family models ([Hines et al. 2024](https://arxiv.org/abs/2403.14720)). That result is for its datamarking and encoding methods; plain delimiting only about halved attack success, and the authors do not recommend it. It is for GPT models, not qwen3:32b, and it uses fixed attacks. Checked against the paper in `c2-verification.md`.
- Adaptive attacks break measured defenses. NIST's CAISI raised attack success on upgraded Claude 3.5 Sonnet from 11% to 81% with new red-team attacks, and from 57% to 80% on average (model not named) just by repeating attacks 25 times ([NIST CAISI](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations)). Any low number you measure is a lower bound.
- Checks in **code** on the model's output are recommended by OWASP: "use deterministic code to check that outputs follow those formats" and "complete mediation" ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/), [OWASP LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). An answer-policy engine fits this.
- Human approval is recommended everywhere, but it has known costs: reviewer fatigue ([2506.08837](https://arxiv.org/html/2506.08837v3)) and automation bias ([NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)).
- Over-abstention is a real, reported cost of safety layers. CaMeL drops from 84% to 77% task success ([2503.18813](https://arxiv.org/abs/2503.18813)). C abstained on 37 answerable runs. A new layer must be judged on useful answers as well as on injection.
- Real SOC copilots publish few measured safeguards. Microsoft's Security Copilot card lists optional classifiers for indirect prompt injection, source citations, least privilege and human review, but gives no injection numbers ([Microsoft Learn](https://learn.microsoft.com/en-us/copilot/security/security-copilot-application-card)).

## 3. Candidate layers mapped to the literature

### 3.1 Tainting / spotlighting tool output, plus an instruction-content scan
- **Literature.** Spotlighting is the best-measured prompt-level defense ([Hines et al.](https://arxiv.org/abs/2403.14720)). Anthropic recommends JSON-encoding untrusted strings and labeling their source, and screening tool output with a small model ([docs](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)). OWASP lists "segregate and identify external content" ([LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) #6).
- **Verdict: worth testing; the most direct fix for the 27%.** Use datamarking or JSON labels, not base64: a local 32B model must still read command lines and user agents to judge them, and base64 adds tokens ([Prompt Shields docs](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection)). The spotlighting numbers are for GPT models; do not expect <2% on qwen3:32b *(unverified)*. Keep the content scan as a tripwire that *flags* evidence, not as the main defense (see Pitfalls). Caution: in triage, an injection attempt inside an alert is itself evidence of an attack. Flag it; do not silently delete it.

### 3.2 Investigation policy in code
- **Literature.** This is the Plan-Then-Execute pattern: decide which tools run before reading untrusted data ([2506.08837](https://arxiv.org/html/2506.08837v3)). It also matches OWASP's advice to handle functions in code, not by the model ([LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) #4).
- **Verdict: good fit, and it may help usefulness more than security.** C made 2.0 calls per run and often abstained before looking (`docs/report.md`). A rule like "always run event search and entity lookup before deciding" attacks that. It protects *which tools run*, but not the *conclusion*, so it will not fix injection on its own. To respect ADR 0001, the policy must use the same tools and fit inside 8 calls.

### 3.3 Answer policy engine (reject "benign" with known-bad indicators; check citations against retrieved ids; one repair retry)
- **Literature.** OWASP: "use deterministic code to check that outputs follow those formats" and "complete mediation" ([LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/), [LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)). OpenAI: aim to constrain impact "even if it succeeds" with deterministic controls ([OpenAI](https://openai.com/index/designing-agents-to-resist-prompt-injection/)). CaMeL shows the general idea of code-enforced policies on data flow ([2503.18813](https://arxiv.org/abs/2503.18813)).
- **Verdict: the strongest candidate, because it is structural and protects the disposition itself.** A planted "this is benign" cannot pass if code sees known-bad indicators in retrieved evidence. Limits: (1) it only works if the indicator list comes from trusted code or data, not from the model; (2) it catches "benign on bad evidence", not other flips; (3) a repair retry is an extra model call, so count it and report it; (4) if a rejected answer falls back to `needs_more_info`, it raises abstention. Report useful-answer rate next to injection. No source gives a measured number for this exact rule in triage *(no evidence found)*.

### 3.4 Action allowlist
- **Literature.** OWASP LLM06 mitigations 1–3 and 7 ([LLM06](https://genai.owasp.org/llmrisk/llm062025-excessive-agency/)); Security Copilot asks for least-privilege agent permissions ([card](https://learn.microsoft.com/en-us/copilot/security/security-copilot-application-card)).
- **Verdict: cheap and standard, but low marginal value here.** Tools are already read-only and the gate never executes. It would mainly make proposed actions cleaner for the reviewer. Do it, but do not expect it to move the injection number.

## 4. Pitfalls

1. **A regex or keyword scan is weak by itself.** No source reports a measured detection rate for string rules. Attackers paraphrase or encode; Microsoft lists "Encoding Attacks" as a whole attack class ([Prompt Shields](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection)). Even trained classifiers are "fundamentally heuristic" ([2506.08837](https://arxiv.org/html/2506.08837v3)), and Willison calls a 95% catch rate "a failing grade" in security ([blog](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)). Also, a scan tuned to this repo's own injections will look good on them and fail on new ones. Use a held-out set of injection phrasings.
2. **Over-abstention is a known cost.** CaMeL pays 7 points of utility ([2503.18813](https://arxiv.org/abs/2503.18813)). C already lost far more. Any layer that rejects or flags evidence can push the model to `needs_more_info`. Always report the useful-answer rate and `abstained_when_could_answer` beside injection success.
3. **Fixed attacks understate risk.** Adaptive and repeated attacks raised success rates a lot in NIST's tests ([CAISI](https://www.nist.gov/news-events/news/2025/01/technical-blog-strengthening-ai-agent-hijacking-evaluations)), and adaptive attacks bypassed 12 recent defenses, most above 90% success ([Nasr et al. 2025](https://arxiv.org/abs/2510.09023), abstract). Call any result a lower bound.
4. **Human approval is not a full safeguard.** Reviewers get tired ([2506.08837](https://arxiv.org/html/2506.08837v3)) and defer to automation ("automation bias", [NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)). And in this project the gate protects actions, not the disposition the analyst reads.
5. **Results may not transfer between models.** Spotlighting and Prompt Shields results are for other models or are not published ([Hines](https://arxiv.org/abs/2403.14720); [Prompt Shields](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection), mainly English).
6. **Deleting injected text can hide the attack.** In a SOC, an injection string in a log is a signal. Prompt Shields' "no attack detected" result "doesn't establish that the document is trustworthy" either ([docs](https://learn.microsoft.com/en-us/azure/ai-services/content-safety/concepts/jailbreak-detection)).
7. **Vendor claims are not measurements.** Security Copilot reports "strong protection rates" with no numbers ([card](https://learn.microsoft.com/en-us/copilot/security/security-copilot-application-card)). Treat as claimed.
